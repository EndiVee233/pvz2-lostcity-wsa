# 第十轮：修改标记与保存请求恢复并编译

本轮继续扩展独立 C++ 工程，恢复四个原生函数并编入实际静态库：[profile_dirty.cpp](../../native_recovered/src/profile_dirty.cpp)。现在可编译的原生语义操作由此前五项增加到九项。

| Ghidra 地址 | 恢复操作 | 字段/调用依据 |
| --- | --- | --- |
| `007210c4` | 标记 PlayerInfo 已修改 | `+4` 浮点字段；更新修改时间并请求保存 |
| `0071a924` | 更新修改时间 | `+0x4d4`；正服务时间优先，否则使用 `time(0)` |
| `007b8ed0` | 设置待保存并通知存储调度 | 管理器 `+0x80` 标记；`+0x81` 和全局字节控制调度 |
| `00721ce4` | 写入创建时间并标记修改 | `+0x1ec`；随后尾调用修改入口 |

结构声明加入这些已确认字段和编译时偏移断言，避免将宿主指针大小混入 ARM32 布局。

## 恢复出的行为

PlayerInfo 的 `+4` 为负数时直接执行修改流程，不读取时钟单例；否则仅当它小于时钟单例的 `+0x24` 时执行。执行时将该字段改为 `-1.0f`，更新时间，再调用管理器保存请求入口。尚未完整确认该浮点字段的业务含义，源码采用中性名称 `pending_time`，没有将它误作布尔值。NaN 比较不触发修改，正无穷不触发，负无穷触发。

管理器保存请求始终把 `+0x80` 置为 1。只有管理器 `+0x81` 和全局阻止字节均为零，才取得存储对象并调用其虚表 `+0x10`。因此阻止通知并不清除待保存标记。此处只确认存储调度调用边界，不能将这个回调本身当作文件已写入的证据。

`0071a924` 先调用服务访问器，取得正时间值时使用它；非正值时读取系统时间。`00721ce4` 写入 `+0x1ec` 后调用同一修改流程，补充了上一轮创建路径的证据。

## 验证与构建

原始 ARM 检查通过 16 项：浮点边界 8 项、时间选择 3 项、两级保存门控组合 4 项、创建时间设置及尾调用 1 项。检查对象内存变化范围、回调顺序、栈和被调用方保存寄存器。时钟/管理器单例使用已初始化路径；浮点比较辅助函数、时间服务、存储访问由钩子代替，单例首次分配路径尚未覆盖。

可编译 C++ 对应 47 项检查通过，覆盖浮点短路、NaN/无穷、时间回退、门控及字段设置；原有 18 项档案管理检查也通过。使用 Zig 0.13.0，实际重新编译、归档、链接并执行两个程序，退出码均为 0。标准 CMake 构建文件已加入新源文件和检查目标，但本轮仍只实际运行 PowerShell/Zig 构建路径。

工程产物为 `native_recovered/build/pvz2_profiles.lib`、`profile_tests.exe` 和 `dirty_tests.exe`。本轮没有修改 APK 或用户存档。

新增操作保留 `DirtyServices` 接口，以表达尚未恢复的服务与存储依赖；检查程序提供受控实现。它们已编入静态库，内存 ProfileStore 尚未自动接入这些调度接口。原生注册表、完整文件加密序列化、存储调度器实现及完整游戏引擎仍未达到源码重建。
