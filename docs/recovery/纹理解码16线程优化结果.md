# WSA 纹理解码线程优化

日期：2026-10-30。

## 完成的修改

`publish_repo/src/glshim/glshim.cpp` 中 ASTC 分条解码的线程上限由 4 改为 16。
实际线程目标取 `min(16, 在线 CPU 数, 分条任务数)`；CPU 数查询失败或只有一个
CPU 时，在调用线程上解码。WSA 实际报告 20 个在线 CPU。

大于等于 1024×1024 像素的纹理会按 ASTC 块行边界进一步分条，使原本任务不足的
大纹理也能使用更高并发。保持完整分辨率、RGBA 输出及原有缓存格式；RGBA4444
和 ETC1 的独立转换路径没有改为 16 路。缓存根目录可以通过
`PVZ2_GL_CACHE_ROOT` 指定，独立测试包继续使用自己的私有缓存目录。

修正了旧实现在线程创建部分失败时，线程句柄数组可能出现空洞、随后错误 join 的问题。
成功创建的句柄连续保存；线程不足时由现有工作线程处理全部任务，全部创建失败则
由调用线程处理。日志新增目标上限、选取数量、成功创建数量和任务数。

## 构建与像素验证

使用本地 Android NDK r30、API 21、ARMv7、C++17 和本地 astc-codec 源码重新构建，
静态链接 libc++。源码、Windows 构建脚本和 Android 检查程序位于
`publish_repo/src/glshim/`。构建脚本通过标准输出接收编译产物，避免本机 NDK
直接创建输出文件时出现的 EACCES；不需要改变系统权限。

在 WSA 中实际运行 `test_decode`，14 个解码场景通过，每个场景将所有输出像素与
同一 codec 的串行解码结果逐字节比较。覆盖 ASTC 4×4、5×5、6×6，1031×1027
非整块边缘、257×259 小图、16 线程、单 CPU、间隔线程创建失败和全部创建失败。
另检查 CPU 数查询失败、8 CPU、任务数不足、零任务和 16 线程上限。

测试输入来自本地 astc-codec 的 `atlas_small_{4x4,5x5,6x6}.astc`；较大纹理由其
有效压缩块重复构成。未将这些输入记为真实游戏启动纹理。测试对线程调度的 CPU
查询结果分别注入 4 或 20，运行主机仍为同一台报告 20 CPU 的 WSA。

| 4096×4096 ASTC 6×6 测试图 | 成功创建线程 | 解码耗时 |
| --- | ---: | ---: |
| 4 路 | 4 | 2879 ms |
| 16 路 | 16 | 1174 ms |

该次样本减少约 59.2% 的解码时间，约 2.45 倍速度；不包含游戏全流程、纹理上传或
缓存写盘耗时，不保证每个场景获得相同收益。

证据：`native_analysis/glshim-threads16-device-tests.log`、
`native_analysis/glshim-threads16-build.log`、
`native_analysis/glshim_threads16/build/build-validation.json`。
