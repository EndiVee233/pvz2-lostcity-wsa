## WSA 实测

原版应用已存在于 WSA，故测试包使用独立应用 ID `com.popcap.pvz2cthd.reconstruction`、独立组件授权地址和独立数据目录。未卸载原版，未清除其数据。测试前原版可以显示公告及网络/云存档故障提示。

首个测试包实际执行了恢复后的 Java 解包流程，日志记录完成 **2,745,361,062 字节**，随后因独立包名与资源表包名不一致，在旧 SDK 的布局查找中出现资源 ID 0 崩溃。修复方式是只在独立验证包中同步修改资源表 `0x7f` 包名，保持资源编号和其余内容不变；正式重建包仍保留原资源表。

最终 v3 测试包使用本轮四个 Java 模块。已核对 WSA 中实际安装 APK 的 SHA-256 与本地 v3 文件一致；所有 DEX 和原生库与对应正式重建包一致。

最后又完整构建了一次工程，APK 容器哈希发生变化；复核脚本逐项比较了最终输出与已测试 v3 包，确认 DEX、原生库和其余有效载荷内容一致，资源表仅有上述独立包名差异。运行记录保留最初实测来源哈希，构建记录另行标注内容对应关系，未将二者冒充为同一归档文件。

## 构建结果与继续方向

最终包保留 8 个 DEX、50,457 个类；与原 APK 比较，1,726 个非 DEX 条目的哈希一致，包括 8 个原生库和两个资源包。原 APK 的哈希保持不变，签名和对齐校验通过。构建脚本默认编译这五个 Java 文件，支持 `-OriginalBootstrap`、`-OriginalBridge` 回退。

构建工具使用限制内存的 JVM 配置；大体积测试包使用先推送、再安装的方式，避开先前安装流传输导致的连接中断。签名候选文件验证通过后才替换正式输出，避免中断留下不完整的正式 APK。

下一步应继续恢复 `SexyAppFrameworkActivity`、HTTP 事务和原生桥接等模块，并在可控测试数据下验证更多流程。原生游戏引擎仍需要按类型、对象布局和函数控制流逐块重建；现有 55,207 个函数伪代码尚未形成可从 C/C++ 编译的游戏核心。
