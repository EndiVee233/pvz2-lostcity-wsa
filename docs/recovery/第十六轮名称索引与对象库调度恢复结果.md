# 第十六轮：名称索引写入、绑定与双表对象库调度

本轮恢复类型名称和对象名称索引的写入/删除，并接通真实驻留池、描述符、槽位与名称句柄解析。对象库创建的双表选择、扩容、复用、槽位发布和四个转发器安装调度也已恢复，完整构造器仍保留服务边界。

源码：[engine_name_index.hpp](../../native_recovered/include/engine_name_index.hpp)、[engine_name_index.cpp](../../native_recovered/src/engine_name_index.cpp)。当前完整游戏仍不能从源码生成可运行 APK。

## 新增行为与来源

| Ghidra 地址 | 恢复行为 |
| --- | --- |
| `011ea54c` | 无符号名称编号精确查找 |
| `011ebbec` / `011ebc9c` | 类型名称树的唯一插入位置、提示插入及值更新接入 |
| `011eab1c` | 类型名称树的整体删除遍历 |
| `011ed354` / `011ed404` | 对象名称树的普通/提示插入位置 |
| `011ed520` | 对象名称节点分配、驻留引用取得、重复候选节点清理和插入 |
| `011ead38` | 名称节点连接与计数增加，调用已恢复的平衡算法 |
| `011ea120` | 对象名称树整体删除，按原遍历顺序释放名称引用 |
| `011ee270` | 删除/设置对象名称到槽位描述符的绑定，返回成功或失败 |
| `011eefb0` | 双表对象库取得/创建的调度 |

共十一项核心原函数行为。`011e7cb4` 的 reserve 和 `011eab5c` 的默认追加也在对象库调度中直接执行并核对；源码按此调用语境实现逻辑容量/增长，不将这两个通用向量函数的所有分支另计为已恢复。地址沿用 Ghidra 加载偏移 `0x10000`。

名称树使用 `recovered_rb_tree.hpp` 的已恢复旋转、插入平衡、删除移植和平衡，没有采用 `std::map`。类型树值为编码类型编号；对象名称树值为三字描述符。对象名称节点持有驻留引用，分配时 retain/read 文本，删除时 release；重复插入的候选节点也会经历 retain/read/release。类型名称树节点本身不持有引用，原引用所有者位于尚未完整恢复的对象库/包元数据中。

整体删除对象名称树时递归处理右子树，再释放当前节点并沿左子树继续。该顺序会影响驻留池的空闲队列和编号复用，源码与取证均保留。

## 绑定顺序

`011ee270` 在反编译伪代码中被标为 `void`，但实际 ARM 返回成功值 1 或失败值 0。恢复接口采用布尔返回值，并直接与原始执行结果比较。

函数首先删除指定名称的旧节点并释放旧引用，然后才检查新句柄。两字全零句柄表示删除映射，返回成功。句柄失效、类型不符或槽位越界时返回失败，但旧映射已经删除；源码没有自行改成失败保留旧值。有效句柄从槽位 `+0x14/+0x18/+0x1c` 复制描述符到新的名称节点。

对象释放只会按已恢复的槽位逻辑移除描述符索引，不会由本轮代码自动删除所有名称别名。名称映射可能暂时保留旧描述符，而解析因描述符已不存在返回空；显式清除别名后才释放其名称引用。本轮动态连接场景对此作了验证，未推断上层游戏可能安装的其他回调。

## 对象库调度边界

`RegistryBanks::ensure` 根据类型编号的 `0x2000` 位选择双表，主表索引清除此位。目标对象库已存在时直接复用。若目标索引达到当前表长度，增长到 `index + 0x10`，保留旧槽位并将新槽位填零。随后调用构造服务，先把对象库写入表，再依次安装面向注册表 `0x34/0x44/0x54/0x64` 的四个转发器。

原指令验证执行真实表 reserve/resize 和转发器向量追加；`011ec764` 的完整对象库构造函数体采用受控实现。C++ 同样通过 `StoreFactory::construct/install_forwarder` 表达构造和外部回调边界。因此本轮证明的是调度行为，尚未恢复构造器中的默认数字名称、`$` 前缀规范化、显示名称、包路径、所有元数据字段、RTTI 或完整事件转发函数体。

## 实际验证

原 ARM 共执行 200 个场景、4,230 个操作后检查点：

| 范围 | 场景数 | 检查点 |
| --- | ---: | ---: |
| 名称索引完整树状态、重复插入、提示回退、无符号键和引用调用次序 | 180 | 2,862 |
| 真实驻留池下的名称绑定、清理、名称句柄规范化和对象解析 | 15 | 1,032 |
| 对象库双表增长、复用、槽位发布及转发器安装顺序 | 5 | 336 |

树状态逐项比较节点颜色、父子连接、键、值、计数、根和最小/最大节点，不使用哈希。绑定场景另外逐项比较真实驻留池的条目、计数、文本、链表及字符串树；真实池中的编号来自原始取得/引用代码。名称 0、重复绑定、替换对象、空句柄删除、无效句柄先删除后失败、失效对象目标和全部别名清理均有覆盖。

低层树场景的 retain/read/release 使用受控边界并比较调用顺序；绑定场景则执行真实驻留池。分配器、libc 内存/宽字符操作与单线程 kuser 比较交换仍为取证环境边界。检查调用后的栈及被调用方保存寄存器。

另有 12 项 C++ 动态模块连接检查，实际使用恢复源码取得对象库视图、创建槽位对象、绑定中文名称、经名称句柄解析，确认扩容后对象仍可访问、释放后目标失效、显式解绑释放索引引用、清空名称句柄后引用归零。此处构造适配器只提供宿主视图，不冒充完整原类型构造器。

## 仍需继续恢复

完整类型构造与注销、包/名称规范化、RTTI、真实对象类和资源载入尚未补齐。ProfileStore 仍使用此前独立的宿主档案后端；完整存档序列化、战斗、渲染、动画、声音和关卡运行时也未完成。

名称视图使用宿主指针，双表记录逻辑容量；宿主分配器和原 ARM32 的地址/二进制 ABI 不等价。检查限于成功分配、有效名称编号和稳定节点；无效提示、失败分配、构造异常、并发和重入不在范围内。调用方必须让驻留池的寿命覆盖对象名称索引。

普通构建无需读取、加载或链接原始 `.so`；取证脚本仍读取原库执行指令。本轮没有修改 APK、安装内容或用户存档。
