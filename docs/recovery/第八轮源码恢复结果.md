# 第八轮：玩家档案生命周期恢复

本轮沿着多存档操作继续恢复原生核心，整理了 10 个相关函数的已有 Ghidra 结果，并将其中 5 个函数改写为带类型、可读的 C++ 语义片段：profile_lifecycle_recovered.hpp（本地材料）。这 10 个函数来自已有全库识别结果，本轮没有把它们重复计为新增识别函数。

## 还原结果

| Ghidra 地址 | 恢复职责 | 本轮处理 |
| --- | --- | --- |
| `007ba9f4` | 按名称切换玩家 | 可读 C++，原始 ARM 分支核对 |
| `007ba95c` | 按旧名称改名 | 可读 C++，原始 ARM 分支核对 |
| `007c0b38` | 昵称子串过滤 | 可读 C++，原始 ARM 分支核对 |
| `007baa74` | 选择注册表首个档案 | 可读 C++ 语义整理 |
| `007bdeac` | 按名称删除档案 | 更正旧命名，可读 C++ 语义整理 |
| `007ba7c8` | 根据名称查找句柄 | 保留伪代码，标明引擎依赖 |
| `007be820` | 创建并初始化档案 | 梳理名称、时间、选择标记、通知调用 |
| `007c0bb0` | 新建前校验 | 梳理空名、过滤、重名及创建路径 |
| `007c13d0` | 改名前校验 | 保留存在疑点的过滤返回值，未擅自修正 |
| `007b98dc` | 当前档案及回退 | 标明选中 ID、注册表查询与默认对象路径 |

旧映射误将 `007bdeac` 命名为 `SelectByName`，现已更正为 `DeleteByName`。真正的切换函数为 `007ba9f4`，只把 PlayerInfo 的 `+0x1ec` 字段复制到 ProfileMgr 的 `+0x74`。这两个字段是引擎选中 ID，不应与存档文件外层的 UID 直接混同。

切换函数的自动伪代码把双字句柄的低字误标为被 OR 运算和其他调用返回值覆盖。原始指令明确用 `ldrd` 读入临时寄存器，句柄本体始终保留在 `fp-0x1c`。本轮用两个均非零的句柄字进行分支检查，确认两次解析收到同一个完整句柄，避免沿用错误伪代码。

低层改名函数不检查昵称合法性或重名，由上层编辑器包装函数负责这些判断。它先更新名称，再调用原同步入口。删除函数会通知、移除对象，然后选择注册表中的首个剩余档案并进入同步路径；返回值为 0（失败）、1（仍有档案）、2（删除最后一个）。它自身不直接写 `pp.dat`，因此 v4 在删除确认回调中加入本地保存有明确依据。

`007c13d0` 的伪代码显示：昵称过滤未通过时写入 `[FILTER_WARNING]` 却返回 1。该路径尚未单独验证，未将其擅自改成失败返回，也未把它纳入已验证的 C++ 函数。

## 验证范围

验证记录（本地材料）包含 13 项原始 ARM 检查：切换与改名各 3 项，过滤 7 项。验证了返回值、对象内存变化范围、改名和同步调用顺序、过滤提前退出、栈及被调用方保存寄存器。句柄查找和解析、字符串搜索、引用释放、同步均使用受控钩子，未模拟完整引擎或存档数据库。

C++ 片段使用后端接口表达尚未恢复的引擎依赖，宿主字符串与容器不兼容游戏原生 ABI。它尚未编译或链接到 APK。首档回退和删除两项为语义整理，没有包含在这 13 项 ARM 检查中。完整引擎、注册表生命周期及文件序列化仍需继续恢复。

本轮不修改游戏、存档和已安装的 v5 APK。最新可运行结果仍为 v5；没有为仅分析代码重复构建安装包。

复现：`python scripts/recover_profile_lifecycle.py`。原库完整 SHA-256 校验及原指令导出均由脚本记录。
