## 百分比为何不能直接给

已编译源码生成的 169 个类，相对全包 50,457 个类只是类数量口径；PopCap 命名空间 169/170 也只覆盖 Java 启动/桥接层。大量第三方类可以通过对应源码依赖构建或替换，无须逐个手工反编译；主要游戏逻辑又集中在原生引擎。这些比例都不能代表整游戏恢复率。

现有整库取证包含 39,842 个导出目标、39,819 份成功导出的伪代码材料。伪代码仍需类型、布局、接口和行为恢复；116 项已登记语义操作与这些目标不是同一计数单位，部分标量入口和单类装载路径未冒充完整通用函数。尚没有足以计算整库功能权重覆盖率的清单，因此整体百分比保持未定义。

能明确量化的目标距离是：**原引擎核心替换 0/1；源码引擎 Android 启动未达成；源码引擎进关卡未达成。** 目前不是最后的打包收尾阶段。

## 后续关键路径

1. **闭合外部资源图并补齐模式。** Cowboy DangerRoom 的本地五个声明工厂已支持，下一步需 LevelModules、ZombieTypes、HeroTypes 等外部类和加载链，解决当前 16 条未闭合引用；同时补齐通用模式、GameFeature、UID/文本 RTID 和更多值类型。数据闭环不等于游戏行为已恢复。
2. **恢复可运行的游戏核心。** 场景、关卡、实体、更新调度，以及渲染、动画、音频、输入和资源生命周期需要可编译实现并组合验证；这部分体量不能由当前工具检查数估计。
3. **建立 Android 源码引擎目标。** 实现 JNI/系统接口，使用 Android 工具链生成 ARM 库，替换 libSrc；梳理其他旧库哪些需要源码替换，哪些 SDK/附加功能可以移除。当前保留 8 个旧库，不代表必须原样逆向全部 8 个。
4. **完成纯源码整包与设备验收。** 整理剩余托管依赖和资源构建，从干净环境生成 APK；构建输入中排除原引擎与原 Smali 回填后，验证冷启动、关卡操作和存档。此前使用旧引擎成功运行的测试包不能替代这一验收。
